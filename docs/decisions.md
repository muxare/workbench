## 2026-11-11: A person holds a list of roles, derived from `roles_changed` events (by Claude)

- **A human teammate has `roles`, a non-empty list without repeats, instead of one `role`.** Stage 1 of `docs/dev-loop.md` puts Mikael on the board as product owner, designer, frontend and backend developer at once, and a single role could not say that. `teammateRoles` in `packages/shared/src/domain.ts` is the list of `teammateRole` values, at least one and each once. The order is the person's own: the first role is their main role. An empty list is refused rather than read as "no role yet", because the board, the profile and the AI's eligibility all need to know what a person does.
- **The roles are derived from events, not stored.** "Every change is an event" (2026-11-09) names roles as one of the settings that must leave a trace, and the process profile already follows that pattern, so `roles_changed` joins `mode_changed` as a teammate event with `from` and `to`. `from` is empty only when a person joins. The store's `addTeammate` writes the teammate row and appends the joining event (`roles-<id>-joined`, made by the person), and removes the row again if the event is refused, so a person never exists without roles. A change after that goes through `appendEvents` like any other: the subject and the actor must be people, `to` must differ from `from`, and `from` must be the roles the person holds now, so two changes made from the same view cannot both win (409). `POST /api/teammates/:id/roles` with `{ actor, roles, was }` appends one, answers with the teammate, and appends nothing when the person already holds those roles in that order. Any person may change anyone's roles; there is no sign-in, so this guards against mistakes, not abuse. Keeping a `roles` column as the starting value and events only for later changes was rejected, because then two places would hold one fact. There is no screen for changing roles yet; the next task, starting a board with a real team, is where people are added.
- **Seed data says when the team joined.** `SeedData` has `joined_at`, and `seed` passes it to `addTeammate`, so the joining events sit at the start of the stream with a time that fits the data rather than the time of seeding. The invented seed uses the start of Sprint 1, 2026-08-31T06:00Z, so its four joining events fall in Sprint 1's cycle log and leave Sprint 4's untouched. `seedEvents` in `apps/api/src/store.ts` lists every event the seed stores, joining included, which is what tests compare stream positions against. The invented people keep one role each, because the laundry room example's cast has one role per person.
- **Migration `0004_teammate_roles_events`** was generated by drizzle-kit (it drops the `role` column) and edited by hand, as `0002` was: before the drop, each person's stored role becomes a `roles_changed` event from no roles to a one-element list, made by the person and stamped with the time of the migration. A test migrates such a database. A person with no stored role, in a database made before `0001`, gets no event and still fails to read; reseeding remains the fix, as recorded on 2026-11-09.
- **A person's chain covers every role they hold.** `chainOf` in `apps/api/src/profile.ts` lists every function whose `role` is one of the person's roles, in file order, then the other functions they have a mode for. The AI's profile uses the same rule, so a person holding several roles is listed as the owner of each of their roles' steps.
- **Seat order: a person sits once, at the seat of their main role.** The board seats by the first role in the person's list: `po` above the board, `ux` on the left, `fe` and `be` on the right, with people whose main role is `fe` above those whose main role is `be`, and people sharing a main role in the API's order, as before. Seating someone at every role's seat would show one person several times, and a fixed rule such as "the earliest of their roles in the order po, ux, fe, be" would put a developer who also orders the board at the top, whatever they consider their main job; letting the list's order decide keeps that choice with the team. With all four roles first-listed as `po`, Mikael sits above the board. Would change if people find the main role confusing, or if the board grows a seat that shows several roles at once.
- **Labels: the main role in short, every role on the panel.** Avatars, the lines between teammates, log lines and card detail use the main role's label ("PO") and title, so a line stays as short as before. The panel heading is the main role's title, and a new muted mono line under it, "Also UX · FE · BE", names the others; the profile's breadcrumb lists every role title. The product owner's summary line ("Owns the order and the milestone.") now shows only when none of the person's roles owns a chain of functions; a product owner who also designs or develops gets mode counts, because they work steps of their own. A `roles_changed` line in the logs reads "BE joined the team as BE" or "PO changed BE's roles to BE, FE · was: BE". The board folds a streamed `roles_changed` into the person at once, as it does a mode change. The artboard draws one role per person, so the "Also" line is an addition no artboard shows.
- **Design review** (the `design-reviewer` subagent, which could be spawned this time, against `Main.dc.html`, `Profile.dc.html` and the README tokens): the "Also" line matches the panel's mode-count line (mono, 11.5px) in the `muted` token, the panel's sizes and copy are unchanged, and a single-role breadcrumb reads as the artboard's. Kept as they are: the "Also" line and the mode counts sit together in the same type, told apart by colour only, which the reviewer rated low-confidence and the artboard has no precedent for; and the roles in a log line are joined with ", " where the panel uses " · ", because the log line already uses " · " to separate its clauses ("· was: BE"). Not rendered in a browser. Checked against a seeded scratch database with curl: `POST /api/teammates/invented-po/roles` gave the product owner all four roles, the board returned them with the `roles_changed` event last in its log, and a repeat with the old `was` answered 409.

## 2026-11-11: The coding functions for the development loop (by Claude)

Five functions were drafted for stage 1 of `docs/dev-loop.md`, following template version 1 with no new fields: `implement_services` (be), `implement_interactions` (fe), `fix_bug`, `open_pull_request` and `review_pull_request` (team). They follow `docs/reference/team-process-map.md` where it fits and depart from it where the loop needs every change to reach review the same way.

- **One review function, `review_pull_request`, instead of the map's `review_frontend_pr` and `review_backend_pr`.** The two differ only in what the reviewer reads beside the diff (design review notes or security findings), which fits in context. It allows only `manual` and `assist`: in `delegate` the AI would write the review and the person would only press approve, which is what `decides: human` exists to prevent. The AI critic is the `assist` mode, and it never approves. Its output is the map's `approved_change`; requested changes are not an output but send the card back to the building step, so the step is done only when a person approves. Would change if teams want separate review rules per role that context cannot carry.
- **`fix_bug`, `open_pull_request` and `review_pull_request` have role `team`.** The map files `fix_bug` and `open_pull_request` under frontend, but backend changes and bug fixes need the same steps. A consequence: `team` functions appear on no person's profile unless chosen, because the profile lists functions by the person's role, as `write_issues` already does.
- **`fix_bug` outputs `bug_fix`, a branch, not a pull request as in the map.** Every building step (`service_code`, `working_ui`, `bug_fix`) ends with commits on the card's branch, and `open_pull_request` makes the pull request from any of them, so one artifact, `pull_request`, has one maker. `open_pull_request` takes all three as optional inputs, because the template cannot say "exactly one of"; the structural rule `one_change` enforces it. If more functions need that, it is a case for a template field, not added now.
- **Left out from the map:** the preview build from `open_pull_request` (this repository has none), and the inputs from undrafted frontend steps (styled UI, frontend tests, accessibility report, performance report, design review notes, approval rules). Inputs from undrafted steps that the building functions cannot do without were added as artifacts and are supplied by hand, as `ui_spec` already is: `tasks` and `backend_spec` (write_spec_and_tasks), `ui_components` (scaffold_components), `api_mocks` (agree_contract) and `bug_report` (debug_failure, as the map says, though most bugs are reported by a person; an open point in `fix_bug`).
- **New artifacts:** `tasks`, `backend_spec`, `ui_components`, `api_mocks`, `bug_report`, `service_code`, `working_ui`, `bug_fix`, `pull_request`, `approved_change`. The structural checks speak of "the project's check command" and "the card id in the branch name" rather than `pnpm check` and `wb/<card id>-…`, so the functions hold for any project; the workbench's own conventions appear only in examples. All examples continue the invented laundry room project.
- **`docs/dev-loop.md` was underspecified on one point and is corrected.** It said "the coding functions … have to be drafted" as if the map named them all; it names no single pull request review, and puts a pull request in two places (`fix_bug` and `open_pull_request`). It also did not say how the loop's steps 3 to 5 map to functions when a card names exactly one function. The doc now says which function serves which step and lists, under "Not decided here", whether opening and reviewing the pull request are steps on the building card or cards of their own.

## 2026-11-09: Each log has one team-wide filter, recorded as `log_filter_changed` events (by Claude)

- **A filter belongs to the team, one per log, and starts by showing everything.** This settles the question left open in "Every change is an event, and each log chooses which events it shows". The card, board, cycle and teammate logs (`logName` in `packages/shared/src/domain.ts`) each have exactly one filter that everyone sees. A per-person filter was the alternative, but the app has no sign-in, so there is no "me" to keep it for, and a shared board is easier to talk about when everyone sees the same log. Would change with sign-in, if people want their own view; a person's filter could then be a teammate event that overrides the team's.
- **The filter stores what a log hides, not what it shows.** `log_filter_changed` carries `log`, `hidden` (the whole set the log hides from now on) and `was_hidden` (the set it hid before), plus `id`, `actor` and `at`. Storing the hidden set means a log nobody has touched needs no event to show everything, and an event type added to the schema later shows in every log at once, rather than being missed by every filter written before it existed. Storing the whole set rather than one type added or removed keeps the derivation trivial and makes each event readable on its own in a log. The event types come from `streamEventType`, which is built from the card and teammate schemas; `log_filter_changed` itself is the one type written by hand there, because its schema refers to the list, and a test checks the list against `streamEvent`.
- **It is the first event about the whole team: it carries neither `card_id` nor `teammate_id`.** `teamEvent` joins `cardEvent` and `teammateEvent` in `streamEvent`, and `eventSubject` already answered `team` for such an event. No migration was needed: migration `0002_teammate_events` had already made both subject columns nullable. It reaches every browser over `GET /api/events` like any other event.
- **The store checks a filter change the way it checks a mode change.** The actor must be a person (403 through `forbidden`, since nobody but a human sets how the team reads its logs); `was_hidden` must be what the log hides now, compared as sets, so two people changing the same filter from the same view cannot both win (409 through `conflict`); and the change must change what the log hides. Staleness is checked before the last rule, so a stale request that asks for what its view already showed is a conflict, not a request to undo someone else's change. Earlier changes in the same write count, as for status and mode changes.
- **The current filters are derived, not stored.** `deriveLogFilters` takes the latest `log_filter_changed` per log, as `deriveProfile` takes the latest `mode_changed` per function, and the store's `logFilters` runs it over the stream. `GET /api/board` returns them as `log_filters`, and `POST /api/logs/:log/filter` with `{ actor, hidden, was_hidden }` appends one event through `appendEvents` and answers with every log's filter. `was_hidden` is what the caller's view showed, passed through to the event, so the store's 409 reaches HTTP: a browser that changes a filter someone else changed after it last loaded is refused, not allowed to overwrite the other change silently. (The first build filled `was_hidden` from the server, which made that check unreachable over HTTP; a review on 2026-11-09 caught it.) The route stores both sets in schema order, refuses an unknown log with 404, and appends nothing when the log already hides exactly the requested set, as the mode route does for a mode already chosen. `logFilters` reads `type = 'log_filter_changed'` in stream order on every board fetch, so migration `0003_events_type_index` (generated by drizzle-kit) adds an index on `events (type, seq)`; `EXPLAIN QUERY PLAN` shows `SEARCH events USING INDEX events_type_seq (type=?)` with no sort step. An index-backed predicate on the subject columns was the alternative, as `modeChanges` uses the teammate index, but a team event has neither id and `IS NULL` on two columns cannot use the existing indexes; an index by type also serves any later setting derived from one event type. A small route of its own (`GET /api/logs/filters`) was not added, because the board is the only reader today and it already refetches on every event.
- **A filter is applied only where a screen shows a log.** The API never filters: the board response's `log`, the card response's `log`, the stream, the AI teammate's run and anything the learning layer will read keep every event. The board's own log in the browser also keeps every event, because card detail and the profile page watch it to know when to reload. `shownInLog` in the shared package applies a filter, and the web app calls it in three places: the log under the board (`logLines`), the card detail's log (`cardLogLines`) and the AI teammate's "What I did last" (`recentLines`), which is a teammate log; checks, questions and the card's mode on card detail still read the whole card log, and the rest of the AI profile reads its whole response. "What I did last" filters the AI profile's ten latest events, so a filter that hides common types shows fewer than ten there. A streamed `log_filter_changed` replaces its log's filter in the browser at once (`boardState.ts`), so a change made in another browser applies without a reload. Because the board fetches the latest 50 events and then filters them, a log that hides common types can show fewer than 50 lines; the line count follows from that, and "Show all" says how many are shown.
- **The log under the board takes the board log's filter.** The Main artboard calls it "Cycle log", but what it shows is the board log, the latest events of the whole stream, with no cycle window; the board response has no cycles. Applying the cycle filter there would make that filter mean two things once a real cycle log exists. So the cycle filter is stored, served and settable through the API, but no screen applies it yet, because the cycle log has no screen. The teammate filter applies to the AI profile's "What I did last", which has the same filter control beside its heading; a person's profile shows no log, so it has none. Would change if Mikael wants the panel under the board to be the cycle log in name and data; then it should read the cycle window and the cycle filter together.

It works the first eligible card, as `teammate:run` does; choosing a card over HTTP was left out because nothing in the design calls for it yet, and the runner's `cardId` option is there when something does. Events reach SSE clients through the store's `onAppend`, like the routes' own writes. The provider is the deterministic stub unless `createApp` is given another; no model is called.
- **Refusals follow the board API's conventions.** An unknown teammate is 404, because it is the resource the path names, as an unknown card is. A teammate that is not an AI is 422, a broken rule rather than a bad body or a conflict. No eligible card is 409, not 422: the request is well formed and allowed, and it fails only because of the board's current state, which can change when someone moves a card to Ready, the same reason a pick of a card that is not ready is 409. A card that changes while the teammate works is also 409, through the store's `conflict`. A provider that asks someone who cannot decide is a fault on the server's side, not the caller's, so it falls through to the generic 500.
- **An optional timer runs a step every `TEAMMATE_INTERVAL_MS` milliseconds for the teammate `TEAMMATE_ID` (default `invented-ai`), and it is off unless that variable is set.** The demo is about an AI that works alongside people, and an AI that picks up a card shortly after someone moves it to Ready shows that better than one that waits for a button. It is off by default so tests, development and anyone looking at the board never see it change unasked. The interval must be a whole number of at least 1000 ms, so a typo cannot flood the board; a tick is skipped while the previous one runs, so a slow provider never works two cards at once; and a failing tick is logged and the timer keeps going. It lives in `apps/api/src/teammates/timer.ts` and is started from `main.ts`. Would change when a real provider makes each run cost money, at which point the trigger should become an event (a card entering Ready) rather than a poll.

## 2026-11-08: The board API and its event stream (by Claude)

- **One resource per thing a person does, all under `/api`.** `GET /board` returns the cards with derived status, the teammates, the open questions, the latest 50 events and `last_seq`; `GET /cards/:id` returns a card with its log and questions. Writes are POSTs: `/cards` (a new card in backlog), `/cards/:id/pick`, `/cards/:id/questions` (ask), `/cards/:id/questions/:questionId/answer` and `/cards/:id/status`. Each write answers with the card as it now stands and the events it appended. Request and response schemas live in `packages/shared/src/api.ts`, and the routes are chained so `AppType` can type a Hono client in `apps/web`. There is no sign-in yet, so every write names its `actor`; would change when authentication arrives and the actor comes from the session.
- **Pick, ask and answer are their own endpoints, not status moves**, because each records more than a status: a pick records the mode, an ask the question, an answer the decision. A pick uses the mode the card's owner set for its function in their process profile; a request that names another mode is refused, as is a card whose owner has no mode for it. An ask needs a card in progress and moves it to Needs input, waiting on the person asked. An answer closes an open question and, if the card waits on that question, returns it to In progress. `POST /cards/:id/status` allows only the moves in `manualMoves` (backlog and ready both ways, in progress to review or back to ready, review to in progress or done), and its body names `from`, so two people moving the same card cannot both win.
- **Every refusal is a 4xx with an `ApiError` body (`error`, a readable `reason`, and zod's `issues` for a bad body).** A malformed or non-JSON body is 400, an unknown card or question 404, a non-human answer 403, a stale `from` or a card in the wrong state 409, and any other broken rule, such as an unknown function, an unknown teammate or a move that is not allowed, 422. The store says which kind of rule it enforced through a new optional `code` on `StoreError`; existing callers are unchanged.
- **Writes that append more than one event are atomic.** The new `appendEvents` checks each event against the stream as the ones before it leave it, then stores them in one multi-row insert, so a pick never leaves a `picked` event without its status change. Writes to one database run one at a time, so a check and its insert cannot interleave with another write. `appendEvent` now goes through the same path, with the same signature and checks.
- **The SSE stream fans out from the store, not from the routes.** `onAppend` in the store calls every listener once for each stored event, so events the AI teammate writes straight to the store reach the browsers as well as those written through the API. Each connection to `GET /events` fixes its starting point before it answers, subscribes, replays what the client missed from the table, then sends live events, skipping any it already sent. The SSE `id` is the event's position in the stream (`seq`), so `Last-Event-ID` resumes exactly; a first connection can start from the board's `last_seq` with `?after=`, and without either it starts at the end. Messages are unnamed (`onmessage`) with the event as JSON in `data`, unlike the tutorial, which names each message by event type; one handler is simpler for the board. An idle stream sends a comment every 25 seconds. The limit is that only writes in the same process are pushed live; a write from another process is seen only on the next reconnect's replay. Would change when the store moves to Postgres, where `LISTEN`/`NOTIFY` can carry appends between processes.
- **`zod` became a direct dependency of `apps/api`**, the same version as `packages/shared`, because the API parses request bodies with the shared schemas and needs `ZodError`. It has no install scripts.

## 2026-11-08: AI teammate behind a provider interface, with a stub provider (by Claude)

- **The AI teammate lives in `apps/api/src/teammates/` and is split into a runner and a provider.** The runner (`runner.ts`) decides which card the AI may take and which events it appends; the provider (`provider.ts`, `TeammateProvider`) only does the work. A provider gets a `WorkContext` (the card, its function definition read from `process/`, the mode, that mode's protocol, the card log, the owner, the AI itself and the teammate list) and returns a `WorkStep`: a `note` posted as a `report_posted` event and a `question` with `asked_of`, `text` and `why_it_blocks`. Keeping the rules in the runner means a model can never widen what the AI is allowed to do; changing the model is a change of provider only.
- **The only provider is a deterministic stub (`stubProvider.ts`), used by the tests and the demo; no model is called yet.** It builds its note from the function's inputs and the protocol's `note`, and asks about the function's `tacit` items in turn, because tacit knowledge is by definition what only a person can supply. Everything it writes is marked invented. A deterministic provider keeps the tests exact and lets the demo run without a key or network. `pnpm --filter @workbench/api teammate:run` runs one step against the seeded database. It is not wired into HTTP; the API task does that.
- **A Claude provider would default to `claude-opus-5-5`**, the current Opus and the default model in Anthropic's guidance ($4 / $20 per million input / output tokens), with effort set explicitly to `low` or `medium` for this short, structured job rather than switching to a cheaper model. One question per card is a small volume, and the quality of the question is the point of the demo, so the saving from `claude-sonnet-5-5` ($2 / $10) or `claude-haiku-5-5` ($0.10 / $0.50) is not worth the risk. The model id would be configurable. Would change if the teammate runs on many cards per cycle and measurement shows a cheaper model asks equally good questions.
- **Eligibility is read from the function files and the owner's profile, never hardcoded** (`eligibility.ts`). A card is eligible when it is in Ready; its owner is human; the mode is the owner's choice for the function, or `modes.default` when the owner has none, and is in `modes.allowed`; the mode is one this teammate works in; that mode's protocol has `asks` of `ai` or `both` and `decides` of `human`; and, where `opens` is `human`, a human moved the card into Ready. The one fixed list is `TEAMMATE_MODES = ["assist"]`, which is the teammate's own capability, not a function field: `delegate` (the AI drafts) is not built.
- **`opens: human` is read as "a person put the card in Ready".** The template says who opens the work but not what opening is in the app. The seed already has the AI picking `assist` cards, so opening cannot mean picking; the status change into Ready is the nearest human act. Would change if the template or Mikael defines opening differently.
- **A run appends five events through `appendEvent`: picked, ready to in progress, the report, the question, and in progress to Needs input with `waiting_on` set to the person asked.** The runner refuses a question to anyone but a human teammate, because `decides` is always human, and it never appends an `answered` event or a status change out of Needs input. The provider is called before anything is appended, so a failing provider leaves the card as it was. The five appends are not one transaction; the store has no transaction export yet, and a crash between appends would leave a partial run. Would change when the API adds transactions or a second runner can run at the same time.
- **Card links are not checked.** In the invented seed the only eligible card, `invented-152`, depends on `invented-151`, which waits on a person, and the AI still picks it. Nothing in `docs/` says whether `depends_on` blocks a pick. Would change if Mikael decides it should; then the check belongs in `eligibility.ts`.

## 2026-11-08: Event store in SQLite through Drizzle (by Claude)

- **The SQLite driver is libSQL (`@libsql/client` 0.18) with Drizzle ORM 0.45.4, the current stable release.** It needs no install scripts (its native binary arrives as a prebuilt optional dependency), so `allowBuilds` in `pnpm-workspace.yaml` is unchanged. It is a first-class Drizzle driver with batches, transactions and an in-memory database for tests, and a `file:` URL for local runs. `better-sqlite3` was rejected because it compiles a native addon in an install script. Node's own `node:sqlite` was the first choice, since it adds no dependency at all, but stable Drizzle has no driver for it: only the 1.0 release candidate (`drizzle-orm@1.0.0-rc.5`, 2026-10-21) does, and on 0.45 it would mean hand-writing an adapter for the `sqlite-proxy` driver, which loses transactions. Would change when Drizzle 1.0 is stable, or when the store moves to Postgres as `docs/architecture.md` plans.
- **Migrations are generated by drizzle-kit from `apps/api/src/db/schema.ts`** (`pnpm --filter @workbench/api db:generate`) and applied by the app when it opens the database, so the tables are never described twice. drizzle-kit is a dev dependency and is used only for `generate`; its esbuild install scripts were already allowed.
- **Only events, teammates, cycles and the stable fields of cards are stored.** A card's status is the `to` of its latest `status_changed` event, or `backlog` before any, so the stream stays the one record of what happened. The card log is a card's events, the board log is every event (the app has one board), and the cycle log is every event whose `at` falls in the cycle's window, end excluded. All three are ordered by the stream's own sequence number, oldest first.
- **A cycle is a named time window** (`cycle` in `packages/shared`): the design's "Sprint 14". `docs/architecture.md` named the cycle log but did not define a cycle, so the schema was added and the domain model updated. Times are also stored as epoch milliseconds, because ISO strings with different offsets do not compare correctly as text.
- **`appendEvent` checks each event against the stream before writing it**: it must parse with the shared `cardEvent` schema, a status change's `from` must be the card's current state, and an `answered` event's actor must be a human teammate, because `decides` is always human. Cards must name a function found in `process/functions`, read at runtime. Transition rules beyond `from` belong to the API task.
- **The invented seed lives in `apps/api/src/seed/invented.ts`** and goes through the same checks as live writes. It follows the cards in the design concept, and its tests check that every name is marked invented, that every function exists in `process/`, and that every pick uses the mode the card's owner set for that function.
