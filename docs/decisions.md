# Decisions

Newest first. Each entry: what was decided, why, and what would change it.

## 2026-11-09: Card detail and the answer flow (by Claude)

- **`GET /api/cards/:id` now returns the card's function front matter as `function`, or null when `process/` no longer defines it.** The Card artboard shows who opens, asks, writes and decides, what the card reads and writes, and who signs off, and all of that is in the function file. Sending it with the card keeps the rule that the app never hardcodes a function's fields, and costs one field rather than a new endpoint. It is read from `process/functions` on each request, as the AI teammate's run already does, so an edited function file shows without a restart. Would change if the teammate profile needs every function at once; then a `GET /api/functions` would serve both screens.
- **Routing is the URL hash: `#/` is the board and `#/cards/<id>` is a card** (`apps/web/src/route.ts`). It needs no router dependency and no server rewrites for the static build, and other screens add one case each. A card tile's title is a link that covers the tile. Would change when the app needs more than a handful of screens or real URLs for sharing.
- **The card screen has no event stream of its own.** `useBoard` already follows `/api/events` at the app level; card detail refetches `GET /api/cards/:id` whenever the board shows a new event on the card or a new status for it. Checked in Chrome on 2026-11-09 against a seeded scratch database: answering on the screen moved the card to In progress, and an answer posted straight to the API updated an open card screen without a reload.
- **A person answers as the teammate the question was asked of; a question asked of an AI is answered as the card's human owner.** There is no sign-in, every write names its actor, and the API only accepts a human answer because in every protocol a human decides. The form says who it answers as. Would change with sign-in, when the actor becomes the person signed in.
- **The design review's findings and how each was handled.** The answer options under the question (two answers, "Ask AI to compare both", "Pass to Frontend") and the header's "Reassign" are left out, because the API has no answer options on a question, no way to ask the AI to compare, no way to pass a question to someone else and no reassign; each needs a model change, not just UI. Without options the answer is free text, so the field is labelled "Answer, and why (kept in the decision log)" rather than the artboard's "Why". "Answer and resume" appears in the header only when the card waits on that question; another open question gets its own "Answer" button, since answering it does not resume anything. The artboard colours a partly passing check in the `manual` orange; the app uses `needs-input` for a failed check and `assist` for a pass, because `manual` means "I do it" and the check event has only passed or failed. Check results show the event's summary, not the artboard's "6 of 7 pass" count, which the event does not carry. The outputs show artifact ids in mono and no draft number, because there is no artifact title or version in the data yet. The sign-off line now reads "<approver> sign off", as on the artboard. The connection indicator in the header, the "Answering as" line and the card tile's hover and focus outline are additions the artboard does not draw; they are kept because a live screen without sign-in needs them.

## 2026-11-09: A role on every person, and the board seats and labels by it (by Claude)

- **A human teammate now has a required `role`: `po`, `ux`, `fe` or `be`.** The board needs to know who is the product owner and who the backend developer to seat them and label them as the Main artboard does, and a person's name cannot tell it that. The first board build guessed from list order and initials, and its design review listed role abbreviations and seat order as gaps the API could not close. An AI teammate has no role; it sits under the board and is labelled "AI" as before. `docs/architecture.md` now names the role in the domain model.
- **The list is derived from the function roles, not written a second time.** `teammateRole` in `packages/shared/src/domain.ts` is `po` followed by `functionRole` (from `process/template.md`) less `team`. `team` owns the shared steps that anyone on the team carries out, such as `write_issues`, so it describes a kind of function and not a kind of person; nobody is hired as "team". The product owner is the one person role with no chain of functions in `process/` yet, so `po` is added here and only here. Adding a function role to the template therefore adds a person role too, which is what should happen: whoever owns a new chain needs a seat on the board. A test pins the derivation. Would change if the product owner gets function files of their own (then `po` moves into `functionRole`) or if a team has a member whose role owns no chain, such as a tester.
- **The role is stored in a nullable `role` column on `teammates`** (migration `0001_teammate_role`, generated by drizzle-kit), null for AI teammates, like `process_profile`. The board API returns it with no change of its own, because `GET /api/board` already returns teammates through the shared schema. A database created before this migration gets the column but no values, and its people then fail to read; the only such databases are local scratch copies of the invented seed, so the fix is to seed again rather than to guess roles in the migration.
- **The invented seed gives each person the role of the functions they own**: the product owner `po`, the UX designer `ux`, the frontend developer `fe` and the backend developer `be`. A seed test checks that every function a person owns, in their profile or as a card owner, belongs to their role or to `team`. The seed is otherwise unchanged; it is rebuilt from the laundry room example project in the next session.
- **The board seats people by role and labels them by role.** The product owner sits above the board, UX on the left, and frontend above backend on the right, as on the artboard, whatever order the API lists them in; people who share a role sit together in the API's order. Avatars, the lines between teammates and the cycle log show the role in capitals ("PO", "BE") instead of initials, and a panel's heading is the role's title ("Product owner"), as on the artboard, with the person's name as its tooltip. Two people with the same role share a label, which is a known limit of following the artboard; the name stays one hover away. The role titles live in `apps/web/src/board/teammates.ts`, because they are copy on the screen, not part of the model. Would change when a team has two people in one role on the board often enough that the label has to tell them apart.
- **The product owner's panel says "Owns the order and the milestone." instead of mode counts**, as on the artboard, because the role owns no chain of functions and its counts would only repeat that. The design review of this change also found that the panels' "Now" and "Just finished" lines were muted where the artboard sets them in the text colour; they now are. Its other findings were left as they are: the artboard draws one line from the AI to the person it asks, around the board, where the app draws a line at each end; its status lines carry phrases such as "with AI assisting" or "ordering Sprint 15" that the board data cannot yet derive; and its log joins a move and a question into one line where the app logs two events. None of these depend on the role, and each needs more data or a layout change of its own.

## 2026-11-09: The AI teammate's run is one write, triggered over HTTP or by an optional timer (by Claude)

- **A run now appends its five events (the pick, the move to In progress, the report, the question and the move to Needs input) in one `appendEvents` call, so they are stored together or not at all.** This replaces the claim in the 2026-11-08 entry "AI teammate behind a provider interface" that the five appends are not one transaction; the store has had an atomic batch since the board API landed, and the runner had simply not been moved onto it. The provider is still called before anything is appended, so a failing provider leaves the card as it was. The batch also closes a race the earlier version had: the runner chooses its card outside the store's write queue, so a person could move the card while the provider works. The `picked` event passes the store's checks on its own, and only the move out of Ready is refused, so appending one at a time would have left a pick with no status change. Now the whole run is refused with the store's `conflict` error and nothing is stored. Tests cover that case and a run whose report fails the event schema.
- **`POST /api/teammates/:id/run` runs one step of the named AI teammate and answers like every other write: the card as it now stands and the events appended** (`teammateRunResponse` in `packages/shared/src/api.ts`, the same shape as `writeResponse`). It takes no body. Other writes name an `actor` because the actor goes into the events; here the actor is the teammate in the path, and no event records who pressed the button, so asking for one would be a field nothing reads. It works the first eligible card, as `teammate:run` does; choosing a card over HTTP was left out because nothing in the design calls for it yet, and the runner's `cardId` option is there when something does. Events reach SSE clients through the store's `onAppend`, like the routes' own writes. The provider is the deterministic stub unless `createApp` is given another; no model is called.
- **Refusals follow the board API's conventions.** An unknown teammate is 404, because it is the resource the path names, as an unknown card is. A teammate that is not an AI is 422, a broken rule rather than a bad body or a conflict. No eligible card is 409, not 422: the request is well formed and allowed, and it fails only because of the board's current state, which can change when someone moves a card to Ready, the same reason a pick of a card that is not ready is 409. A card that changes while the teammate works is also 409, through the store's `conflict`. A provider that asks someone who cannot decide is a fault on the server's side, not the caller's, so it falls through to the generic 500.
- **An optional timer runs a step every `TEAMMATE_INTERVAL_MS` milliseconds for the teammate `TEAMMATE_ID` (default `invented-ai`), and it is off unless that variable is set.** The demo is about an AI that works alongside people, and an AI that picks up a card shortly after someone moves it to Ready shows that better than one that waits for a button. It is off by default so tests, development and anyone looking at the board never see it change unasked. The interval must be a whole number of at least 1000 ms, so a typo cannot flood the board; a tick is skipped while the previous one runs, so a slow provider never works two cards at once; and a failing tick is logged and the timer keeps going. It lives in `apps/api/src/teammates/timer.ts` and is started from `main.ts`. Would change when a real provider makes each run cost money, at which point the trigger should become an event (a card entering Ready) rather than a poll.
- **Correction to the 2026-11-08 entry on the AI teammate.** Its bullet "Card links are not checked" no longer holds: the later 2026-11-08 entry made an unfinished `depends_on` block a pick, and `eligibility.ts` uses that rule. Its remark that the teammate is not wired into HTTP is also superseded by this entry.

## 2026-11-08: The TypeScript validator replaces the Python one (by Claude)

- **`pnpm validate` now runs `packages/shared/src/functionValidator.ts`, and `checks/validate_functions.py` is deleted**, together with `requirements.txt`, which only listed PyYAML for it. `pnpm check`, the `Stop` hook, `AGENTS.md`, the README, `docs/architecture.md`, `process/template.md` and `process/artifacts.md` now point at `pnpm validate`. The `validate:ts` script is gone. This was task 7 in `docs/next.md`; one validator cannot drift from another, and the API needs the TypeScript one anyway. The `Stop` hook read its JSON with `python3` because the validator already required it; it now uses `node`, so the repo no longer needs Python at all.
- **The parity test is replaced by a test that pins the output.** `functionValidator.test.ts` lists every line the validator prints for the invented fixtures in `packages/shared/test-fixtures/broken-process`, and requires `process/` to pass with no errors. New fixtures cover the cases below. Any change in what the validator reports now shows up as a failing test, to be updated on purpose.
- **Behaviour changes from the Python, each a gap or an unintended oddity found by the port:**
  - `decides` must be `human` in every protocol the file contains, not only in protocols for allowed modes. A protocol for a mode that is not allowed, with `decides: ai` or no `decides`, is now an error. The other actor fields are still checked only for allowed modes.
  - The validator never stops with a crash. An artifact without `made_by` is reported once (`<id> has no made_by`) and skipped in the `from` and maker cross-checks, where the Python raised a KeyError. An artifact entry with no id, an entry that is not a mapping, a list of artifacts that is not a list, invalid YAML in any file, front matter that is not a mapping, and any section or item of the wrong shape (`inputs`, `context`, `outputs`, `checks` and its layers and rules, `checks.human`, `modes`, `modes.allowed`, `protocols` and each protocol, `writes_back`) now give an error line naming the file and the field. A missing or unreadable `template.md` or `artifacts.md` is reported the same way.
  - Errors and notes are printed sorted. The Python looped over a set of modes, so its order changed from run to run.
  - `template: yes` (a YAML 1.1 boolean) is no longer accepted as version 1. More generally, booleans no longer equal numbers anywhere.
  - A plain string in `modes.allowed` is an error (`modes.allowed must be a list`), where the Python split it into characters and reported each as an unknown mode.
  - Two function files with the same `name` are an error on the second (`name '<name>' is already used by <file>`); the first keeps the name in the cross-checks. The Python let the later file silently replace the earlier one. The summary line now counts function files whose front matter could be read, not distinct names.
  - An empty `severity:` reports `severity is empty; write error or warning, or leave it out`, where the Python reported it as an unknown severity.
- **Everything else is unchanged**, including the wording of every other message and how values print in them (`None`, `True`, `['a', 'b']`). There is still no check of the protocol `note` field, because whether the template should name it is an open question for Mikael.

## 2026-11-08: The board API and its event stream (by Claude)

- **One resource per thing a person does, all under `/api`.** `GET /board` returns the cards with derived status, the teammates, the open questions, the latest 50 events and `last_seq`; `GET /cards/:id` returns a card with its log and questions. Writes are POSTs: `/cards` (a new card in backlog), `/cards/:id/pick`, `/cards/:id/questions` (ask), `/cards/:id/questions/:questionId/answer` and `/cards/:id/status`. Each write answers with the card as it now stands and the events it appended. Request and response schemas live in `packages/shared/src/api.ts`, and the routes are chained so `AppType` can type a Hono client in `apps/web`. There is no sign-in yet, so every write names its `actor`; would change when authentication arrives and the actor comes from the session.
- **Pick, ask and answer are their own endpoints, not status moves**, because each records more than a status: a pick records the mode, an ask the question, an answer the decision. A pick uses the mode the card's owner set for its function in their process profile; a request that names another mode is refused, as is a card whose owner has no mode for it. An ask needs a card in progress and moves it to Needs input, waiting on the person asked. An answer closes an open question and, if the card waits on that question, returns it to In progress. `POST /cards/:id/status` allows only the moves in `manualMoves` (backlog and ready both ways, in progress to review or back to ready, review to in progress or done), and its body names `from`, so two people moving the same card cannot both win.
- **Every refusal is a 4xx with an `ApiError` body (`error`, a readable `reason`, and zod's `issues` for a bad body).** A malformed or non-JSON body is 400, an unknown card or question 404, a non-human answer 403, a stale `from` or a card in the wrong state 409, and any other broken rule, such as an unknown function, an unknown teammate or a move that is not allowed, 422. The store says which kind of rule it enforced through a new optional `code` on `StoreError`; existing callers are unchanged.
- **Writes that append more than one event are atomic.** The new `appendEvents` checks each event against the stream as the ones before it leave it, then stores them in one multi-row insert, so a pick never leaves a `picked` event without its status change. Writes to one database run one at a time, so a check and its insert cannot interleave with another write. `appendEvent` now goes through the same path, with the same signature and checks.
- **The SSE stream fans out from the store, not from the routes.** `onAppend` in the store calls every listener once for each stored event, so events the AI teammate writes straight to the store reach the browsers as well as those written through the API. Each connection to `GET /events` fixes its starting point before it answers, subscribes, replays what the client missed from the table, then sends live events, skipping any it already sent. The SSE `id` is the event's position in the stream (`seq`), so `Last-Event-ID` resumes exactly; a first connection can start from the board's `last_seq` with `?after=`, and without either it starts at the end. Messages are unnamed (`onmessage`) with the event as JSON in `data`, unlike the tutorial, which names each message by event type; one handler is simpler for the board. An idle stream sends a comment every 25 seconds. The limit is that only writes in the same process are pushed live; a write from another process is seen only on the next reconnect's replay. Would change when the store moves to Postgres, where `LISTEN`/`NOTIFY` can carry appends between processes.
- **`zod` became a direct dependency of `apps/api`**, the same version as `packages/shared`, because the API parses request bodies with the shared schemas and needs `ZodError`. It has no install scripts.

## 2026-11-08: AI teammate behind a provider interface, with a stub provider (by Claude)

- **The AI teammate lives in `apps/api/src/teammates/` and is split into a runner and a provider.** The runner (`runner.ts`) decides which card the AI may take and which events it appends; the provider (`provider.ts`, `TeammateProvider`) only does the work. A provider gets a `WorkContext` (the card, its function definition read from `process/`, the mode, that mode's protocol, the card log, the owner, the AI itself and the teammate list) and returns a `WorkStep`: a `note` posted as a `report_posted` event and a `question` with `asked_of`, `text` and `why_it_blocks`. Keeping the rules in the runner means a model can never widen what the AI is allowed to do; changing the model is a change of provider only.
- **The only provider is a deterministic stub (`stubProvider.ts`), used by the tests and the demo; no model is called yet.** It builds its note from the function's inputs and the protocol's `note`, and asks about the function's `tacit` items in turn, because tacit knowledge is by definition what only a person can supply. Everything it writes is marked invented. A deterministic provider keeps the tests exact and lets the demo run without a key or network. `pnpm --filter @workbench/api teammate:run` runs one step against the seeded database. It is not wired into HTTP; the API task does that.
- **A Claude provider would default to `claude-opus-5-5`**, the current Opus and the default model in Anthropic's guidance ($4 / $20 per million input / output tokens), with effort set explicitly to `low` or `medium` for this short, structured job rather than switching to a cheaper model. One question per card is a small volume, and the quality of the question is the point of the demo, so the saving from `claude-sonnet-5-5` ($2 / $10) or `claude-haiku-5-5` ($0.10 / $0.50) is not worth the risk. The model id would be configurable. Would change if the teammate runs on many cards per cycle and measurement shows a cheaper model asks equally good questions.
- **Eligibility is read from the function files and the owner's profile, never hardcoded** (`eligibility.ts`). A card is eligible when it is in Ready; its owner is human; the mode is the owner's choice for the function, or `modes.default` when the owner has none, and is in `modes.allowed`; the mode is one this teammate works in; that mode's protocol has `asks` of `ai` or `both` and `decides` of `human`; and, where `opens` is `human`, a human moved the card into Ready. The one fixed list is `TEAMMATE_MODES = ["assist"]`, which is the teammate's own capability, not a function field: `delegate` (the AI drafts) is not built.
- **`opens: human` is read as "a person put the card in Ready".** The template says who opens the work but not what opening is in the app. The seed already has the AI picking `assist` cards, so opening cannot mean picking; the status change into Ready is the nearest human act. Would change if the template or Mikael defines opening differently.
- **A run appends five events through `appendEvent`: picked, ready to in progress, the report, the question, and in progress to Needs input with `waiting_on` set to the person asked.** The runner refuses a question to anyone but a human teammate, because `decides` is always human, and it never appends an `answered` event or a status change out of Needs input. The provider is called before anything is appended, so a failing provider leaves the card as it was. The five appends are not one transaction; the store has no transaction export yet, and a crash between appends would leave a partial run. Would change when the API adds transactions or a second runner can run at the same time.
- **Card links are not checked.** In the invented seed the only eligible card, `invented-152`, depends on `invented-151`, which waits on a person, and the AI still picks it. Nothing in `docs/` says whether `depends_on` blocks a pick. Would change if Mikael decides it should; then the check belongs in `eligibility.ts`.

## 2026-11-08: Event store in SQLite through Drizzle (by Claude)

- **The SQLite driver is libSQL (`@libsql/client` 0.18) with Drizzle ORM 0.45.4, the current stable release.** It needs no install scripts (its native binary arrives as a prebuilt optional dependency), so `allowBuilds` in `pnpm-workspace.yaml` is unchanged. It is a first-class Drizzle driver with batches, transactions and an in-memory database for tests, and a `file:` URL for local runs. `better-sqlite3` was rejected because it compiles a native addon in an install script. Node's own `node:sqlite` was the first choice, since it adds no dependency at all, but stable Drizzle has no driver for it: only the 1.0 release candidate (`drizzle-orm@1.0.0-rc.5`, 2026-10-21) does, and on 0.45 it would mean hand-writing an adapter for the `sqlite-proxy` driver, which loses transactions. Would change when Drizzle 1.0 is stable, or when the store moves to Postgres as `docs/architecture.md` plans.
- **Migrations are generated by drizzle-kit from `apps/api/src/db/schema.ts`** (`pnpm --filter @workbench/api db:generate`) and applied by the app when it opens the database, so the tables are never described twice. drizzle-kit is a dev dependency and is used only for `generate`; its esbuild install scripts were already allowed.
- **Only events, teammates, cycles and the stable fields of cards are stored.** A card's status is the `to` of its latest `status_changed` event, or `backlog` before any, so the stream stays the one record of what happened. The card log is a card's events, the board log is every event (the app has one board), and the cycle log is every event whose `at` falls in the cycle's window, end excluded. All three are ordered by the stream's own sequence number, oldest first.
- **A cycle is a named time window** (`cycle` in `packages/shared`): the design's "Sprint 14". `docs/architecture.md` named the cycle log but did not define a cycle, so the schema was added and the domain model updated. Times are also stored as epoch milliseconds, because ISO strings with different offsets do not compare correctly as text.
- **`appendEvent` checks each event against the stream before writing it**: it must parse with the shared `cardEvent` schema, a status change's `from` must be the card's current state, and an `answered` event's actor must be a human teammate, because `decides` is always human. Cards must name a function found in `process/functions`, read at runtime. Transition rules beyond `from` belong to the API task.
- **The invented seed lives in `apps/api/src/seed/invented.ts`** and goes through the same checks as live writes. It follows the cards in the design concept, and its tests check that every name is marked invented, that every function exists in `process/`, and that every pick uses the mode the card's owner set for that function.

## 2026-11-08: TypeScript port of the function validator (by Claude)

- **`validateProcess` in `packages/shared/src/functionValidator.ts` is a line-for-line port of `checks/validate_functions.py`**, and enforces exactly what the Python enforces, no more and no less. It therefore does not run the zod schema, which is stricter, but takes its roles, modes, actors, required fields, protocol keys, human check keys and body sections from that schema, and reads the template version from `process/template.md` as the Python does. Python behaviour that changes the result (truthiness, `True == 1`, iterating a string, how values print, universal newlines) is reproduced; where the Python would crash, the port throws `ValidatorCrash` instead of reporting something the Python never would.
- **Parity is a test, not a promise.** `functionValidator.test.ts` runs both validators over `process/` and over invented, deliberately broken fixtures in `packages/shared/test-fixtures/broken-process`, one or more per check category, and requires the same printed lines and exit code. Lines are compared sorted, because the Python loops over a set of modes whose order changes between runs. It also compares the fixed lists in the port with the tuples in the Python source, so a change to one side fails the test.
- **The Python validator stays in `pnpm check`.** `pnpm validate:ts` runs the port with the same output. Would change when Mikael decides the port replaces the Python; until then the parity test keeps them together.

## 2026-11-08: Stop hook, domain schemas and the function file schema (by Claude)

- **A project `Stop` hook runs `pnpm check` before Claude may end a turn** (`.claude/settings.json` calls `.claude/hooks/check-on-stop.sh`). The rule that lint, typecheck, tests and the validator pass before handing back must hold every time, and `AGENTS.md` says such rules belong in a hook. On failure it blocks the stop and hands Claude the last 40 lines of output. To avoid a loop it blocks only once: if the checks still fail when Claude Code reports `stop_hook_active`, the turn ends and the failure is shown to Mikael. It runs in the checkout that holds the session's working directory, because `$CLAUDE_PROJECT_DIR` stays on the starting directory when Claude works in a worktree. Every turn now costs about nine seconds of checks; would change if that becomes a nuisance in chat-only turns.
- **Card status is a discriminated union on `state`.** `needs_input` must name the teammate it waits on and the open question's id, and every other state rejects those fields, so a card can never be waiting without saying on whom.
- **Questions are rebuilt from events, not stored as their own record.** The `asked` and `answered` events carry everything needed, and the actor of `answered` is the decider. That decider must be human; the schema cannot see the teammate list, so `decidedByHuman` checks it separately.
- **Card links store only `depends_on`.** "Unblocks" is the same link read from the other card, so the two directions cannot disagree.
- **Domain fields use snake_case**, like the architecture doc and the function files. The event schema is named `cardEvent` so it does not shadow the DOM `Event` type in `apps/web`.
- **Function file front matter has a zod schema in `packages/shared`**, following `process/template.md` version 1, with strict objects so a misspelled field fails. YAML is parsed with the `yaml` package, which has no dependencies, needs no install scripts and runs in the browser and in Node. `parseFunctionFile` works on text and is exported from the browser-safe `index.ts`; reading from disk lives in `@workbench/shared/node`, so `apps/web` never pulls in `node:fs`. Cross-file rules stay in the Python validator until task 12 ports them.
- **The three modes are defined once**, as `functionMode` in `functionFile.ts`; the domain's `mode` is the same schema.
- **Protocols carry an optional `note`**, which every function file uses but `process/template.md` does not list. The schema accepts it; whether the template should name it is an open question for Mikael.
- **Three subagents built these in parallel**, each in its own worktree and branch, and the results were merged and checked together. `.claude/worktrees/` is ignored by git.

## 2026-11-08: Agents, subagents, hooks and skills for building the app (with Mikael)

- **No standing role agents.** No "frontend agent" or "backend agent" with persona prompts. Claude Code splits work per task on its own (Explore, forks), and persona prompts would repeat what it knows and go stale as the stack settles.
